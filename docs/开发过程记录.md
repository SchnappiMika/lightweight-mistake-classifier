## 二、需求与方案确立

### 2.1 申报书确定的技术路线：四层架构

申报书 4.1 明确采用"四层松耦合模块化架构"，并写明各层的职责与创新逻辑。项目实现基本沿这条路线展开，四层的落地位置如下。

| 层次 | 申报书职责 | 申报书所述创新点 | 代码落地 |
|---|---|---|---|
| 多模态数据输入层 | 单条手动录入、TXT/Excel 批量导入、图片/音频本地导入；格式校验与类型分流 | 多格式标准化分流，用户不必预先转换格式、拆分题干 | `app/ui/pages/page_import.py`、`app/core/dataio/`、附件归档 |
| 多模态特征预处理层 | 按学科、题型执行预处理，提取多维度分类特征 | 分类型可插拔单元，单模态可独立优化 | `app/core/preprocess/`：`text_cn`、`text_en`、`formula`、`figure`、`audio` 单元与 `base.py` 注册表 |
| 多特征融合分级分类层 | 关键词粗筛 3—5 个候选，再做多特征融合精匹配；TF-IDF 与余弦相似度作纯文本兜底 | "粗排—精排"两阶段解耦，无需复杂模型训练 | `app/core/classify/`：`coarse.py`、`fine.py`、`weights.py`、`vector_space.py`、`engine.py` |
| 可视化交互与结果输出层 | 结果展示、按自定义维度导出 Excel、自建体系、人工修正 | 零代码配置，并打通"修正—特征库迭代"闭环 | `app/ui/`（三栏布局、`BasePage`、`guide.py`、`workers.py`）、`app/core/dataio/exporter.py` |

架构文档同时锁定了两条实现约束：依赖方向严格单向（`ui → core → models/config`），`core` 层不出现任何 PyQt 导入，因此核心逻辑可以在无图形环境下测试；页面之间不互相持有引用，全部通过 `AppContext` 的信号（`questions_changed`、`scheme_changed`、`feedback_changed`、`toast/status`）通信。这两条约束后来成了自动化回归能在 offscreen 环境下大规模运行的前提。

### 2.2 关键算法设计

**第一层：关键词粗筛。** 倒排索引为"词 → [(标签, 权重)]"，并加三重机制：用 `jieba.cut_for_search` 做子词扩展，权重乘 `SUBWORD_DISCOUNT=0.35`，只补召回、不让弱相关标签挤掉强相关标签；按 `sqrt(关键词数 + 1)` 做长度归一化，避免关键词多的大标签通吃；一个关键词都没命中时按先验补齐到 `COARSE_MIN_K=3`。候选标签数不超过 `top_k` 时直接跳过粗筛。

**第二层：多特征融合精匹配。** 文本、公式、题型、学科四个通道各自算 TF-IDF 余弦相似度，再按 `(学科, 题型)` 分桶加权。例如高数公式题为文本 0.35、公式 0.45、题型 0.10、学科 0.10；英语听力为文本 0.60、公式 0.02、题型 0.28、学科 0.10。某条题没有公式特征时，空通道的权重按比例摊给其余通道（`redistribute`），而不是白白扣掉。

**增量 TF-IDF。** 需求硬性要求"无需全量重训"，因此没有使用 `TfidfVectorizer.fit()`，而是自维护 `vocab`、`df`、`n_docs`，`add_document(tokens)` 为 O(本题词数)。`idf(t) = log((1 + n_docs) / (1 + df(t))) + 1`，与 sklearn 的 `smooth_idf=True` 逐位一致，并由 `test_idf_formula_matches_sklearn` 用真实 `TfidfVectorizer` 逐词比对锁死。

**标签画像 base/delta 双层。** `effective_tf = clip(base_tf + delta_tf, 0)`；`base_tf` 由分类体系的关键词与标准样本重建、不持久化，`delta_tf` 来自人工反馈、持久化。只存 delta 的理由是：base 是用户手改关键词的产物，持久化它会和用户编辑打架——用户删掉一个关键词，画像里却还留着。

**公式—知识点映射。** LaTeX 不能直接分词，`\int_{0}^{1} x\,\mathrm{d}x` 切碎后是 `int`、`0`、`1`、`x`、`mathrm`、`d`，不同知识点的公式碎片高度雷同。项目用 `tools/build_formula_map.py` 生成 `resources/formula_map.json`，85 条正则规则把公式结构特征映射成知识点特征词。三个设计点：带上下限的 `\int` 必须先于裸 `\int` 匹配（规则顺序敏感）；`subject` 字段限定规则的适用范围（`E=mc^2` 只在物理题映射为"质能方程"）；`weight` 用重复注入实现，不另加加权逻辑。

**人工反馈增量优化。** 一次 `apply_correction` 做四件事：按 IDF 加权把本题判别特征并入正确标签的 `delta_tf`，每次注入总质量固定；对误判标签中与本题重合的词按比例衰减且不下穿 0；按感知机式 `Δw = lr · (右通道得分 − 错通道得分)` 只更新对应的 `(学科, 题型)` 桶；把学到的 top-N 判别词以 `COARSE_LEARNED_WEIGHT=0.55` 的折扣并入粗筛倒排索引。最后一步是后来补的，因为冷启动时粗筛召回只有 91%，正确标签进不了候选集，精匹配再准也翻不了盘。

### 2.3 为什么选择传统文本分类而不是大模型

这一选型在申报书中是明确的工程约束，不是事后追认，依据有三类。

第一，部署条件。申报书 4.3.1 写明"所有工具均采用开源、轻量化、支持本地 CPU 离线运行的方案，无云端大模型依赖"；4.2.2 写明"无需复杂深度学习模型支撑，在普通个人电脑上即可流畅运行"。项目的目标用户是普通大学生，使用场景是自己的笔记本，不假设 GPU、不假设常驻网络。

第二，成本与隐私。立项依据指出，主流错题工具把自动分类、批量导出放在付费会员里，OCR 和知识点匹配还要单独付费，学生群体难以长期承担；错题本身包含个人学习记录，本地处理可以避免上传。大模型无论走 API 还是本地部署，都会重新引入费用或硬件门槛。

第三，可解释与可维护。系统要让不懂编程的学生自己建维度、建标签、填关键词、导样本、调权重，并且改完立即生效。关键词、样本、权重都是可见、可改、可解释的；大模型的判断依据难以让非技术用户核对和纠正。开发文档也把这条写进了设计决策："重依赖全部可选 + 优雅降级——学生装不上 1.5GB 的 PyTorch 就用不了，这不可接受。"

需要如实说明边界：项目没有做"传统方法 vs 大模型"的对比实验，因此本文只把上述内容作为选型理由，不表述为"实验证明传统方法更准"。相反，独立语料的迁移结果（科学 190 题中正确 91、弃权 31、错误 68）说明传统方法在跨语料、英文题目上的能力有限，这些局限保留在第七节，不用选型理由掩盖。

### 2.4 需求分析阶段确定的工程约束

- 人工修正必须"无需全量重训"，一次修正的代价是 O(本题词数) 或 O(1)。
- 自建体系保存后立即影响分类，不改代码、不重启。
- 识别的原始结果、用户草稿、确认结果必须分开，只有确认内容参与分类。
- 运行期只读本地模型，准备阶段联网与运行期离线分开记录。
- 所有重依赖可选，缺依赖时降级并明确告知用户，而不是让"识别不出来"变成无法排查的谜。
- 数据保护只承诺已验证范围，不写"任何故障都不丢数据"。

### 3.1 修复前现状评估（文件未记日期）

**目标。** 判断现有原型能否支撑申报书的功能与结题要求，把"看起来有"与"实际可用"分开。

**发现的问题。** 评估时 190 项测试已经通过，但仍能稳定复现一批操作缺陷：关键词输入倒序、自建体系选中后不生效、修改题干后旧分类仍然有效、跨体系保留悬空标签、标签改名不同步、空题被计为分类成功、清空学习成果不彻底、评测脚本可能清空真实工作区、批处理失败不恢复状态。另有一批交付缺口：没有双击启动入口、没有用户可用的完整备份恢复、识别引擎全部不可用、打包脚本排除了 torch/pix2tex/PaddleOCR/Whisper、spec 仍含旧绝对路径。

**评估结论。** 项目被定位为"已有主要模块的功能原型"，不宜直接宣称申报书目标已完成。这一判断后来成为所有结题材料的共同基调。

**验证结果。** 190 项通过、8 条警告、约 26.20 秒；155 条同源数据上知识点 98.1%、纯文本 98.8%、粗筛召回 100%；主评测均值约 8.3ms、P95 约 13.3ms；多特征消融单通道 98.1%、融合 98.1%，没有总体增益；反馈实验同类子集 27 条 74.1%→81.5%（+7.4pp）、全部 78 条 73.1%→75.6%（+2.6pp）、概率论子集 6/8→5/8；特征评测文本/公式/图形 100%、英语 93.3%；155 条评测记录均未关联媒体路径，图形仅 8 条、听力仅 3 条。

### 3.2 第一批（2026-10-27 记录）：启动与核心文本流程

**目标。** 让软件能被普通同学启动，并修掉会造成操作错误、结果不可信、数据风险的 P0 问题；验收标准是用户能独立完成一条真实文本题的完整流程，修改后结果正确更新。

**发现的问题与修复方式。** 下面十项均有复现记录、原因定位和修复，不是"顺手优化"。

**（1）没有可靠的启动入口。** 评估时目录里没有 dist 可执行文件，也没有双击脚本；检查时默认 Python 缺少全部核心依赖，临时验证环境不等同于用户日常启动环境。修复为新增 `启动软件.bat`，自动检查并准备独立运行环境，补充 `开始使用.md`，缺依赖时给出可理解的处理办法。期间 Qt 初始化挂起，一度把环境临时放到用户目录；后定位到 PyQt5 把中文插件路径误读为问号，改为显式配置真实插件路径，环境得以留在项目 `.venv`，无需删除或重装解决。

**（2）关键词输入倒序、光标复位。** 向关键词编辑框依次输入 `abc`，实际内容变成 `cba`，样本草稿也会丢。原因是每次输入都触发提交，提交广播体系变化，体系树刷新并重新选中标签，重新载入编辑器导致光标位置和选区复位；位置在 `app/ui/pages/page_scheme.py` 的 `refresh_tree`、`_load_label`、`_on_kw_changed`、`_commit`。修复为不再每次输入都完整重建树与编辑器，改用延迟保存、局部刷新，并保留光标、选区和输入法组合状态。回归覆盖了编辑顺序与样本草稿保留；中文输入法组合输入仍需真人操作验收，这一项后来没有完成。

**（3）自建体系不生效。** 新建高数体系并选中后，对高数题分类，实际使用的仍是"高等数学（默认体系）"。原因是 `page_classify.py` 的 `_start` 按学科调用 `scheme_for_subject`，而 `Repository.scheme_by_subject` 返回该学科第一套体系，没有优先使用用户选择。修复为同学科分类优先使用用户选中的体系，删除当前体系后可回退。回归覆盖了"编辑题目 → 自建体系分类 → 人工修正 → 重新读取已保存数据 → Excel 导出"；每学科默认体系设置等更完整交互尚待完善，从空体系开始的完整连续使用验收未做。

**（4）修改内容后旧分类未作废。** 把已判为"定积分及其应用"的题干改为"求解一阶线性微分方程的通解"，记录仍然 `classified=True`，保留旧特征和旧标签，"未分类"数量为 0，再点"一键分类（未分类）"不会处理修改后的题，反馈学习还可能读旧特征。修复为题干、标注、学科、题型、附件任一变化后，清除派生特征、分类及旧修正状态，标记待分类并刷新相关页面。回归覆盖旧结果失效；分类与前台编辑的并发互斥留到后续处理。

**（5）跨体系保留无效标签。** 在体系 A 人工确认后，向体系 B 应用分类结果，`scheme_id` 已改变，但旧的人工确认标签仍被保留，而该标签并不存在于体系 B。原因是 `app/core/classify/engine.py` 的 `apply_result` 对所有 `corrected` 维度直接跳过，没有核对修正属于哪套体系。修复为重分类只保留同体系内仍然有效的人工修正。回归覆盖；跨体系的人工迁移工具未实现。

**（6）标签改名、删除未同步。** 标签改名后，题目中的 `label_names` 仍保留旧名称，导出也用旧名称；删除标签后的引用清理从代码检查看没有实现。修复为基于稳定 ID 统一解析名称，同步历史标签名称及候选名称；标签、维度或体系消失时作废受影响的分类。回归覆盖标签同步；删除前的影响预览和交互式迁移未做。

**（7）空题被计为分类成功。** 空题没有提取到有效特征、没有标签，应用结果后仍标为 `classified=True`。修复为无有效特征不生成有效分类，批次区分成功、失败和未处理数量。回归覆盖空题统计；识别失败的详细提示留到媒体流程补齐。

**（8）学习成果清空不全。** 某体系的历史学习增量已落盘，但新进程尚未创建对应引擎时执行"清空学习成果"，该体系的增量仍然保留。原因是 `app/ui/context.py` 的 `reset_optimization` 只遍历当前进程缓存的引擎。修复为从持久化层统一清空全部体系的学习数据，并同步缓存、权重、反馈日志与题目状态。回归覆盖学习重置。

**（9）评测可能清空真实工作区。** `tools/evaluate.py` 使用继承的 `MC_WORKSPACE`，并在 `_run_one` 中直接 `shutil.rmtree(ws)`；如果用户把该变量指向真实数据目录后运行评测，会清空该目录。修复为评测始终使用自己创建的临时工作区，删除前校验目录归属，禁止把业务工作区作为清理目标。回归验证：即使外部 `MC_WORKSPACE` 指向有数据的真实工作区，评测也完全不修改它。

**（10）批处理失败未恢复状态。** 批量导入遇到异常时返回空列表，已解析的前序文件结果丢失；引擎建库失败只弹提示，没有统一的进度恢复；停止后仍按原批次总数报告完成；异常弹窗还直接宣称"数据已经自动保存"，没有相应保存结果证明。修复为建库失败也发出结束信号、恢复批处理状态，去掉无依据的保存保证，批次区分成功、失败和未处理。回归覆盖批处理失败清理；取消任务和全部任务互斥仍属后续事项。

**验证结果。** 本机独立测试环境 209 项通过、1 条警告、约 31.75 秒，警告来自既有 pytest 夹具写法，不是测试失败；环境迁回项目 `.venv` 后 210 项通过、1 条既有警告、71.90 秒；`启动软件.bat --check` 退出码 0，Qt 界面环境初始化检查通过；用实际 `main()` 入口在隔离临时工作区启动主窗口再自动关闭，返回 `STARTUP_SMOKE_EXIT=0`。该冒烟采用 Qt offscreen 模式，不替代真实屏幕、输入法、缩放和音频设备验收。第一批没有重新测定分类准确率，也没有以这些修复宣称算法效果提高。

### 3.3 算法与交互缺陷专项（《开发文档》第 8 节，文件未记日期）

这些缺陷不在第一批清单里，但都造成了可观察的错误结果，是项目可信度的一部分。

**次线性词频对小数词频产生负权重。** 原实现 `return 1.0 + math.log(count)` 只在 `count >= 1` 时有意义；delta 层经过增益与衰减会累积出小数，`1 + log(0.2) = -0.61`，被负反馈衰减过的词不是"变弱"，而是反向排斥含该词的题目，负反馈的语义整个翻转。它隐蔽在于让增益扫描出现反常的非单调（`gain=0.1` 反而比 `gain=1.0` 差 6 个百分点）才暴露。修复为只在 `count > 1` 时做对数压缩，`count <= 1` 时退化为线性；两段在 `c=1` 处连续、全程单调不减且非负，对整数词频与 sklearn 完全一致。

**评测脚本的实验之间互相污染。** `tools/evaluate.py` 原先在同一进程里依次跑各实验，jieba 词典、引擎缓存的词表 df、`WeightRules` 的落盘文件会互相污染，后跑的实验拿到被前面改过的起点。后果是增量优化实验的冷启动基线从 74.4% 被压到 67.9%，凭空多算出 6 个百分点的"提升"，一度让人以为达标；同进程的数字依赖执行顺序、不可复现。修复为每个实验派生独立子进程（`--only` 参数），跑两遍数字完全一致。

**正强化淹没关键词库。** 原先 `reinforce` 把题干每个词都加 1.0。冷启动时标签画像只有两三个关键词（质量约 4），一条题干十几个词各加 1.0，一次修正就让噪声质量压过人工关键词 4 倍，L2 归一化后关键词贡献被稀释殆尽；通用词还会在所有标签画像里同步堆积，把画像互相拉近。修复为按 IDF 分配且每次注入的总质量固定，通用词几乎分不到质量，长题干也不会天然比短题干更有话语权。

**`apply_correction` 违反自己的文档契约。** 文档写着"标签未变则返回 None"，代码却照样往画像里灌词。用户把下拉框选回原值只是确认，不是新信息；照灌会让题干里的通用词在已经正确的标签上反复堆积。冷启动实验里 77 次"修正"有 57 次是这种无效确认。修复后标签未变直接返回。

**标签级权重覆盖退回全局兜底规则。** 错误写法是 `merged = dict(DEFAULT_RULES[("*", "*")]); merged.update(override)`。用户只想把某个标签的公式权重拉高，结果其余通道悄悄退回通用规则（文本 0.70…），而不是该学科·题型该有的比例（高数公式题文本 0.35/公式 0.45），同时还丢弃了系统已从反馈中学到的权重。修复后 `override` 的语义明确为"在本桶权重之上打补丁"。

**新手引导 `mapTo` 段错误。** `w.mapTo(self, QPoint(0, 0))` 中 `self` 是引导遮罩层，不是 `w` 的祖先；Qt 的 `mapTo(parent, pos)` 要求 `parent` 是调用控件的祖先，传非祖先属于未定义行为，实测直接 SIGSEGV，整个进程退出。严重性在于新手引导在每个新用户首次启动时自动触发，等于打开就崩；之所以长期没发现，是因为所有端到端测试都设了 `guide_done=True` 跳过引导——测试跳过的路径，恰恰是新用户唯一会走的路径。修复为 `self.mapFromGlobal(w.mapToGlobal(QPoint(0, 0)))`，用全局坐标绕开控件树层级。

**把关键词注入 jieba 全局词典。** 同步分类体系时曾把全部关键词以 `freq=2000` 注入 jieba。jieba 词典是进程级全局的，于是出现三类问题：关键词互相污染，一条"分词作状语"把"现在分词和过去分词作状语"从 `现在分词/过去分词/状语` 变成 `现在分词/分词作状语`，"过去分词"被吃掉；跨学科污染，物理关键词会改变英语题的分词；不可复现，同一道题的结果依赖"之前打开过哪套体系"。原注释"否则粗筛永远命中不了"是错的，粗筛有三重兜底。实测注入只换来 +0.6pp（1 条题），却把英语特征提取从 93.3% 压到 86.7%。已移除并封死。

**精匹配为 0 时把题丢着不分。** 题干"水平渐近线"对关键词"渐近线"：粗筛子串命中并排第一，精匹配按分词算余弦，词形零重叠得 0 分，引擎判空标签，整题被丢掉。修复为精匹配全 0 但粗筛有非兜底命中时采信粗筛，置信度折算到"建议复核"区间。

**其他已修的工程细节。** Excel sheet 名的非法字符 `/ \ * ? : [ ]` 与 31 字符上限（标签叫"阅读/完形"很自然，不处理会导出到一半抛异常）；Windows 保留文件名 `CON`/`PRN`/`NUL`/`COM1` 等建同名文件夹会失败；`index.csv` 必须带 BOM，否则 Excel 双击打开中文乱码；Windows 记事本默认 GBK，编码兜底链为 `utf-8-sig → utf-8 → gbk → gb18030 → big5 → utf-16`；精简系统缺 libpulse 时 QtMultimedia 导入会失败，做成 try-import + 标志位，降级为"用系统播放器打开"。

### 3.4 第二批：数据保存、导入与迁移

**目标。** 做完整备份与恢复入口，覆盖题目、体系、学习数据、设置和附件；统一附件导入到工作区，解决 Excel/CSV 相对路径及跨电脑路径失效；补齐批量导入部分失败提示、重试和重复导入处理；完善任务状态与互斥。验收标准是：用带附件和自建体系的数据备份，迁到一个新工作区后，题目、附件、修正和学习结果都能恢复。

**发现的问题。** 备份方面，原子写入只能减少单文件写到一半的问题，不能保证所有数据永不丢失；没有用户可用的完整备份恢复入口；异常弹窗直接宣称"数据已经自动保存"，没有相应保存结果证明；媒体路径按字符串保存，复制工作区不保证换电脑可用。导入方面，批量导入遇到异常返回空列表，已解析的前序文件缺少保留结果与重试；表格导入的 CSV 相对路径按项目目录解析，附件找不到；重复导入会在用户不知情时堆叠。任务方面，导入缺少明显的重复启动保护，分类期间其他页面仍可修改共享题目或体系，停止后仍按原批次总数报告完成。

**修复方式。** 增加工作区备份包、恢复前备份、损坏数据提示和恢复检查，覆盖题目、体系、学习数据、设置、附件与历史导出；恢复时重定位附件并保留内容哈希；统一把附件复制进受管媒体目录，表格相对路径以源表格所在目录解析并校验存在性；导入按逐文件、逐行收集成功与失败，保留成功项、导出失败清单、支持重试，并提供可选去重与重复提示；统一任务状态，批处理期间锁定或隔离相关编辑（开发进度记录"任务互斥"已落地），按成功、失败和未处理分别计数；保存失败明确提示，不声称已经保存成功。批次取消在文件中没有记为已完成。

**验证结果。** 第二批没有单独验收文档，《第一批修复与后续计划》注明其状态统一记入《开发进度与验收》。该记录中"数据保护"一行写明：ZIP 校验、恢复前备份、失败回滚、附件重定位和保存失败提示都有对应回归，但不保证硬件故障无损；"导入与附件"一行写明支持手动、TXT、XLSX、CSV、TSV，附件归档、去重、部分失败保留与重试。备份包含题库、体系、反馈学习、设置、附件及历史导出，不含运行环境、模型、日志或旧备份。断电、磁盘损坏、无权限、空间不足等故障没有逐项验证。

### 3.5 第三批：图片、公式和听力真正可用

**目标。** 完成识别组件与模型准备流程，展示实际可用状态、本地模型位置与初始化错误；为真实图片 OCR、公式识别、音频转写补齐后台运行、进度、失败重试及结果校对入口；单独验证断网运行与首次安装，记录真实媒体处理耗时。验收标准是分别用真实图片、公式截图和音频完成"导入 → 识别 → 人工校对 → 分类 → 保存和导出"，不能用手填文本代替识别成功。

**发现的问题。** 默认依赖没有安装识别引擎，`tools/build.py` 还明确排除了 torch、pix2tex、PaddleOCR、Whisper；代码直接 `WhisperModel('base')`、`LatexOCR()`、`PaddleOCR` 默认初始化，第三方库首次加载可能联网下载模型，没有本地模型路径配置和离线完整性验证；识别结果只在分类说明里显示截断的摘要，没有完整校对流程；图片识别与 Qt 在同一进程导入 ONNX Runtime 会发生原生访问冲突，普通 Python 异常处理无法拦截；公式依赖与主环境不兼容。

**修复方式。** 固定引擎、模型和依赖版本，准备本地模型目录、校验值、组件安装说明与许可证；运行期只读本地文件，缺文件时明确提示；把"组件已安装、模型已准备、模型正在加载、可识别、识别失败"分开；识别放入独立 `media_worker` 进程，通过文件传递请求与结果，运行库异常退出可转成界面错误；原始识别、用户草稿、确认结果三层分开，只有明确确认的内容参与分类；校对窗口支持查看原图、编辑结果、重试、取消和明确应用；公式使用独立 Python 3.12 runtime 随包携带。

**验证结果。** 图片：实际执行 `安装图片识别.bat`，完成依赖准备、模型校验和独立进程真实图片识别自测；禁止 socket 连接的冷启动进程中识别 7 行（含中文题干和英文选项），引擎耗时约 2.39 秒；原生界面从四行高数印刷图识别，人工补充并应用后分类为"定积分及其应用"，保存、重载、Excel 导出、备份恢复和图片内容检查通过；空白图被明确拒绝。公式：pix2tex 0.1.4 在独立 Python 3.12.13、torch 2.5.1 CPU 环境完成两图推理，Leibniz 裁剪公式输出 `\frac{d x}{d y}\qquad\frac{d^{2}y}{d x^{2}}`，与原图两项一致，含加载约 24.02 秒；1920×1080 质心多公式图形整图输出不可靠的长 LaTeX，约 54.59 秒，属于边界失败。听力：faster-whisper 1.2.1 CPU int8 `base` 完成公开 31.88 秒 WAV 转写，本机与打包进程均成功。三条链路的人工内容复核都未完成，不能把"有输出"当作"转写或识别正确"。

### 3.6 第四批：复习使用与可交付版本

**目标。** 完善查找、低置信度复核、答案和解析等内容字段，以及适合打印的错题本导出；处理混合体系导出；制作并验证 Windows 发布包；请普通同学独立操作并记录问题与修复。验收标准是在未配置开发环境的 Windows 电脑上完成安装或解压启动，以及一整套日常使用流程。

**发现的问题。** 导出页以学科筛选、用一套当前体系决定导出列，混合不同体系或不同自定义维度时可能缺列或混淆；页面每次进入都全量重建，155 题下 `on_show` 导入/分类重建均值约 2461.6/2886.0ms；批量填表时表头自动测宽、排序和绘制拖慢界面；打包后 Qt 自带旧 `MSVCP140.dll` 影响 ONNX/语音原生库加载，识别进程退出；spec 仍含旧绝对路径；没有干净 Windows 设备验证。

**验证结果。** 源码 UI 生命周期与业务流程 55 项通过，新导航/主题/更新机制 6 项通过，增加表头优化后对应 8 项通过，最终完整 348 项通过、1 条既有 `PytestRemovedIn10Warning`、216.58 秒；测试期间有构建负载，该时长不用于性能结论。页面响应用 155 题、每页 3 轮对照，导入/分类重建 `on_show` 均值由约 2461.6/2886.0ms 降至 12.7/11.9ms，无变更导航不调用 `on_show`；该测量采用 offscreen 事件，不代表真实显示器或低配硬件。发布包冒烟 `frozen=true`、`passed=true`，覆盖五页导航、分类保存、Excel、备份、重载、图片 OCR 和听力；图片约 3.14 秒、听力约 12.45 秒、公式约 18.68 秒，整个冒烟脚本约 65.40 秒（不是单题计时）。干净无 Python 的 Windows、macOS、i5-8250U/8GB 低配设备和同学独立试用均未完成；"答案与解析等独立字段"在文件中没有已交付记录，校创清单将其列为可选增强。

### 4.2 Python 3.9 → 3.13.5

申报书 4.3.1 写明"开发环境为稳定适配的 Python 3.9"。实际主环境为 Windows 11 + Python 3.13.5，公式识别另用 Python 3.12。变更原因是新增的 OCR 固定版本要求 Python 3.11 或以上；若为保持与申报书一致而强行降级，会破坏已经工作的功能。《校创结题差距与验收清单》对此的表述是："优先明确经过验证的最终环境和更换理由，不应为形式一致强行降级而破坏已工作功能。"

这项变更留下过一个文档问题：`requirements` 头部曾称 3.9/3.12 均验证通过，与 README 的未实测说明冲突。该表述已按实际重写。Python 3.9 在本项目没有实测记录，因此本文不声称 3.9 兼容。

### 4.3 PaddleOCR → RapidOCR

申报书 4.2.1 和 4.3.1 两处写明用 PaddleOCR 轻量版提取图形内标注文本与参数。实际采用 RapidOCR 3.10.0 + ONNX Runtime 1.31.1（CPU），模型为 PP-OCRv6_det_small（9,929,594 字节）、ch_ppocr_mobile_v2.0_cls_mobile（585,532 字节）、PP-OCRv6_rec_small（21,234,383 字节），合计 31,749,509 字节、约 30.3 MiB，随固定版本 wheel 安装在 `.venv/Lib/site-packages/rapidocr/models`。程序明确指定三个模型的本地路径，识别前检查大小和 SHA-256，缺失或损坏时提示修复；完整校验值保存在 `app/core/preprocess/image_ocr.py`。

替换依据不是"看起来更轻"，而是实际验证：执行 `安装图片识别.bat` 完成依赖准备、模型校验和独立进程真实图片识别自测；禁止 socket 连接的冷启动进程中识别 7 行中英印刷文字，引擎耗时约 2.39 秒；原生界面四行高数图完成识别、人工补充、应用、分类、保存、重载、Excel 和备份恢复。许可方面，RapidOCR 源码为 Apache-2.0、ONNX Runtime 为 MIT，随包 `MODEL_LICENSES.md` 列明模型来源、上游 PaddleOCR 权利归属和分发要求，模型不是本项目自主训练成果。

能力边界：RapidOCR 只做印刷文字的本地提取，不能替代上下标、分式、矩阵、积分等数学结构的可靠转写，后者由公式组件负责；真实拍照、倾斜、阴影、密集排版、小字号、单位与方向标注的效果尚未验收，图形关系理解不在申报要求内，也未实现。

### 4.4 NLTK → 内置英文规则与词形处理

申报书 4.2.1 写明英文文本采用 NLTK 完成分词、词根词缀还原和英文专属停用词过滤。实际未安装 NLTK，改用内置英文规则加词形处理。替换理由是避免为可选能力引入额外依赖和本地语料，与"重依赖可选 + 优雅降级"的整体设计一致。

这是能力替换，不是等价实现，边界必须写清：规则版做的是后缀剥离和词形归一，不是 WordNet 词元还原，对不规则屈折、词性歧义和复合词的覆盖有限。项目后来补了标准英中科学术语对应，保留原文与原英文词元，并修复了英文词形处理、阅读任务结构、阅读与完形特征混用的问题；但最终版本的独立英文验收没有完成，目前只有英语 30 题诊断结果（正确 26），不能当作英语核心特征 ≥90% 的证据。《校创结题差距与验收清单》要求"若继续使用内置规则，说明替换理由、能力限制及实测结果"，前两项已具备，第三项仍缺最终英文专项。

### 4.5 pix2tex 放入独立 Python 3.12 环境

申报书的公式路线就是 pix2tex，项目保留了这一组件，但部署方式改为独立运行时：pix2tex 0.1.4、Python 3.12.13、CPU PyTorch 2.5.1，两个官方检查点 v0.0.1。README 的表述是"公式组件因兼容性采用独立 Python 3.12 环境"，即与主环境 3.13.5 及其他依赖存在兼容性冲突，因此把重依赖隔离出来，避免拖累主包。runtime 位于 `formula_runtime/python/python.exe`，由媒体进程自动调用，默认读取随包模型，用户无需另装 Python 或设置 `MC_MODEL_DIR`；随包迁移已通过真实主 exe 验证。

能力边界：独立环境解决的是"能不能跑"，不是"准不准"。两图实测中，Leibniz 裁剪公式输出与原图两项一致（约 24.02 秒），1920×1080 质心多公式图形整图输出不可靠的长 LaTeX（约 54.59 秒）；同一质心图裁剪首行并反色为 510×210 后输出 `S\underline{{{B}}}`，明显误识别，缩放 50% 至 255×105 后输出 `S\,=\,\int_{a}^{b}f(x)\mathrm{d}x`，与图中首式相符，约 20.64 秒。这说明单公式真实离线流程可用，但对输入尺寸敏感，多式混排必须先裁剪。两图加派生图不构成 ≥90% 的独立准确率，也不能宣布公式指标达成。

### 4.6 Whisper → faster-whisper

申报书要求 Whisper 轻量化模型完成英语听力音频的本地离线转写。实际采用 faster-whisper 1.2.1，CPU int8，`base` 模型约 145MB，随 Windows 包携带。替换目的是在普通 CPU 上以更小的依赖和可接受的包体积完成本地转写，同时保留"运行期不联网"的约束。

实测：公开 31.88 秒 WAV 在本机与打包进程中均转写成功；隔离轮识别耗时 11.319 秒，公开素材验收记录 11,313.3ms，最终发布包约 12.45 秒。人工逐字核对没有完成，否定词、数字和专有名词是否转写正确尚未逐条确认；真实音频格式、时长、损坏/空白和录音质量的组合也没有系统测试。因此现有证据只能说明"能转写"，不能说明"转写准确"，更不能说明听力题分类准确。

### 4.7 未变更与补充说明

- **jieba** 保留用于中文分词，但增加了分学科专有名词词典（否则"洛必达法则"会被切成"洛必达"+"法则"，关键词永远匹配不上）和双层停用词（通用停用词 + 学科通用词，"如图所示"在物理题里出现率极高但零判别力）。关键词不再注入 jieba 全局词典。
- **scikit-learn** 不再承担运行时 TF-IDF，只作为 idf 公式的对照实现；运行时使用自研增量向量空间。
- **PyQt5、pandas、PyInstaller** 保留，未更换框架。打包从"单文件/目录模式"扩展为 GUI 与媒体进程两个独立 Analysis，并采用目录模式交付。
- **版本**统一为 1.0.0，目录包、源码、手册、测试报告使用同一版本号。README 中的软件名为"大学生轻量化错题自动分类管理系统"，申报书文件名则为"基于传统文本分类方法的大学生轻量化错题自动分类管理系统"；最终登记名称仍需按校创清单确认统一，本文不声称名称已经统一。

## 五、多模态链路的落地过程

### 5.1 三条链路共用的结构

**独立识别进程。** 图片、公式、音频的识别都不在主界面进程执行，而是交给 `media_worker.exe`。GUI 与 worker 使用两个独立的 PyInstaller Analysis，通过文件传递请求与结果。直接原因是：本机发现 Qt 初始化后，在同一进程导入 ONNX Runtime 会发生原生访问冲突，普通 Python 异常处理无法拦截；把 Qt 和推理运行库分开加载后，识别在后台等待，运行库异常退出可以转成界面错误。取消与超时会结束识别进程，单条输入错误不会跳过后续题。

> **2026-10-30 更正。** 2026-10-29 的补强让批量识别在常驻进程里复用模型。后续实测发现这条对**图片**不成立：同一进程连续识别同一张 8.7KB 图片，耗时 2.3 秒 → 6.0 秒 → 稳定在 11.4 秒；重建 RapidOCR 模型对象（同进程）仍为 2.3→9.2→12.7 秒，说明是进程级状态累积；而每次新起进程连跑 8 次全部稳定在 2.3–2.5 秒。日志处理器数、活动线程数、可用内存均已排除。故图片改回"一图一进程"，音频与公式仍复用常驻进程（它们加载模型的开销远大于复用代价）。修复后连续 4 张图片为 2.56–2.80 秒/张，全部回归 826 项通过。

**原始/草稿/确认三层分离。** 每条媒体题分别保存原始识别结果、用户草稿和确认结果。保存草稿不会改变已有题干、特征或分类；只有明确"应用为题干"或"确认"才替换文本并使旧分类失效；已有题干不同时先要求确认。关闭窗口再分类时，只使用已保存的题干和标注，不重复运行旧 OCR 追加未经校对的文字。修改已经参与分类的确认内容，会使旧分类失效。这条分层是整个多模态设计里最关键的约束，它把"机器输出"和"用户认可的内容"分开，避免未经核对的识别文字悄悄进入分类。

**失败与取消保护。** 识别失败或取消不得覆盖题干、历史确认结果或现有分类；重新识别成功才更新识别记录；附件变化或丢失时拒绝应用旧识别结果，避免把旧图文字用到新图上；关闭未保存草稿时支持保存、放弃和取消关闭；任务运行中禁止关闭窗口。图片、公式、音频三条链路都按这套规则实现，并由回归覆盖缺模型、损坏文件、取消、附件变化、保存失败和进程异常。

**模型随包与离线边界。** 首次组件准备需要联网；运行期只读取本地模型，缺模型、格式不支持或识别失败会显示原因。模型及运行组件随完整发布目录携带，公式 runtime 由媒体进程自动调用，无需用户另装 Python 或设置环境变量；开发者可用 `tools/check_media_models.py` 检查模型，或用 `MC_MODEL_DIR` 指定模型根目录。识别进程禁止 Python socket 建立网络连接，不接收远程图片地址；但这一限制针对识别进程，不等于对整个系统做了操作系统级断网测试，也不等于第三方库在准备阶段不会联网。准备阶段联网与运行期本地读取在文档中分开记录。

### 5.2 图片链路

**组件与校验。** RapidOCR 三个模型随固定版本 wheel 安装，程序指定本地路径，识别前校验大小和 SHA-256；缺失或损坏时提示修复并重新安装固定版本组件。三个模型随完整发布目录携带（目录保留 `_internal`、`models` 等内容），运行期从包内路径加载。环境自检只检查组件可发现性和文件存在、大小，不加载模型、不下载模型，因此"自检正常"不等于"识别准确"。

**操作流程。** 导入图片并选中题目和学科，打开"图片文字：识别与校对"，点击"开始识别/重试"，对照可缩放原图编辑结果；原图预览默认适应宽度，可选 50%、100%、150%、200%，支持滚动；已核对 Windows 原生渲染的常用尺寸和 760×520 最小尺寸。保存草稿不改变已有题干、特征或分类；只有"应用为题干"才替换文本并清除旧分类。

**保留内容。** 原始识别、逐行结果与模型分数、位置框、附件内容哈希、耗时和应用状态都写入题目存储，随备份保留并可在恢复后重新定位附件、核对哈希。分数明确标注不是准确率。Excel 导出使用已应用的题干，并新增图片识别状态。

**失败处理。** 空白、损坏、丢失、超过 30 MiB 或 2500 万像素的图片会报告错误，不会以空识别内容宣告成功；当前进程超时上限为三分钟，超时结束子进程并提示缩小图片；可取消当前结果，等待计算完成后返回。已核对：识别和保存失败都保留原有题干与分类，保存失败的编辑内容继续留在校对框。

**实测。** 冷启动禁网进程识别 7 行中英印刷文字，引擎约 2.39 秒；原生界面从四行高数印刷图完成识别、人工补充、应用、分类为"定积分及其应用"、保存、重载、Excel、备份恢复和图片内容检查；真实空白图被明确拒绝。这些图片是程序生成的清晰印刷栅格图，确实经过图片解码、模型检测和识别，没有拿预填题干冒充 OCR；但不能代表真实拍照、倾斜、阴影、密集排版或未见题目的准确率。用户独立真实图片样本没有收集，干净电脑验收没有完成。

### 5.3 公式链路

**组件与运行方式。** pix2tex 0.1.4 在独立 Python 3.12.13 + torch 2.5.1 CPU 环境运行，两个官方检查点 v0.0.1，来源与 SHA-256 记录在验收 JSON 中；运行期阻断 socket 连接。没有用 RapidOCR 替代公式识别，因为印刷文字 OCR 不能可靠转写上下标、分式、矩阵和积分。

**预处理与校对。** 支持公式原图选区、反色、尺寸适配和设置恢复；按模型 672×192 上限等比处理，修复了额外 105 像素限高丢失细节的问题。识别结果进入校对界面，保留原始 LaTeX、草稿和确认结果；只有确认后才参与分类，确认后走公式—知识点映射。缺模型提前返回；模型哈希损坏拒绝；识别失败或取消保留原有内容和分类。

**公式—知识点映射。** `resources/formula_map.json` 的 85 条规则把公式结构特征映射为知识点特征词。规则顺序敏感：带上下限的 `\int` 必须先于裸 `\int` 匹配，否则定积分会被误判为不定积分。规则带 `subject` 字段做学科隔离，`E=mc^2` 在物理题里映射为"质能方程"，在高数题里不产生特征，这一点有测试锁死。`weight` 通过重复注入实现，让特征词在 TF-IDF 中自然获得更高词频。

**实测与边界。** Leibniz 裁剪公式输出与原图两项一致，含模型加载约 24.02 秒；1920×1080 质心多公式图形整图输出不可靠的长 LaTeX，约 54.59 秒，应裁剪到单个公式后重试；裁剪首行 510×210 输出 `S\underline{{{B}}}` 属误识别，缩放 50% 至 255×105 后输出与图中首式相符，约 20.64 秒。两次派生结果都保留在 JSON 中，派生图不增加独立样本数。随包 runtime 已由真实主 exe 调用验证。结论只能是"单公式真实离线流程可用且对输入尺寸敏感"，不能外推整体准确率，也不能宣布公式特征提取 ≥90%。

### 5.4 听力链路

**组件与运行方式。** faster-whisper 1.2.1，CPU int8，`base` 模型约 145MB，随 Windows 包携带；音频导入、预览、归档、后台 worker、全文查看、原始/草稿/确认内容、明确应用后英文特征融合均已完成。听力正文与题干问题、选项、标注共同保存；确认后参与分类，未确认时标记为未校对媒体。

**失败与取消。** 与图片、公式共用同一套保护：失败或取消不覆盖题干、上次确认内容和现有分类；重试保留上次确认内容；任务运行中禁止关闭窗口。

**实测。** 公开 31.88 秒 WAV 完成转写，隔离轮识别约 11.319 秒，公开验收记录 11,313.3ms，最终发布包约 12.45 秒；转写成功 1/1。转写文本能够进入英文特征提取并得到"听力理解"标签，自动确认后的分类、Excel、备份和重载链路通过。

**边界。** 人工逐字核对未完成，否定词、数字和专有名词是否正确没有逐条确认；真实音频格式、时长、损坏/空白和录音质量组合没有系统测试。上述结果只能说明本地转写链路可运行，不等于内容准确，也不等于听力题分类准确。

### 5.5 三条链路实测对照

| 链路 | 组件与模型 | 文件记录的实测 | 当前结论 | 主要边界 |
|---|---|---|---|---|
| 图片文字 | RapidOCR 3.10.0 + ONNX Runtime 1.31.1，模型约 30.3 MiB | 冷启动禁网识别 7 行、引擎约 2.39 秒；发布包约 3.14 秒 | 印刷文字提取与校对链路可用 | 清晰印刷图；真实拍照、小字、单位、方向、图形参数未验收 |

### 6.2 隔离与可复现

- **工作区隔离。** 评测和验证使用自己创建的临时工作区，不继承、不删除用户设置的 `MC_WORKSPACE`，不覆盖真实题库。默认用户数据在用户目录 `.mistake_classifier`，文件记录的验证轮次均使用隔离或临时工作区，未替用户操作真实题库。
- **进程隔离。** 评测的每个实验派生独立子进程（`--only`），避免 jieba 词典、引擎缓存 df、`WeightRules` 落盘文件互相污染；跑两遍数字一致才算可复现。
- **哈希留痕。** 独立语料与诊断报告保留数据集 SHA-256、规则代码 SHA-256、报告 SHA-256；同一题目的截图、改写和转写不能跨调试集、反馈学习集和复测集冒充独立样本。
- **旧报告不覆盖。** 页面响应保留优化前后两份记录；媒体识别保留原始结果；公式保留失败图与派生图；诊断改进后明确标注"已用于定位改进，不再视为完全未见独立准确率验收"。
- **模型只读。** 运行期只读本地模型，缺文件明确报错；准备阶段联网与运行期离线分开记录。

### 6.3 发布包冒烟

发布包为 `dist/错题自动分类/` 目录模式，GUI 与 `media_worker` 使用独立 Analysis，模型、第三方运行库、公式 runtime 随目录携带。冒烟记录 `frozen=true`、`platform=Windows-11-10.0.26200-SP0`、`python=3.13.5`，在隔离工作区完成五页导航、分类保存、Excel（7,850 字节）、备份（20,043 字节）、重载、图片 OCR、听力转写、自动确认后的分类/导出/备份/重载。单条图片约 3.14 秒、31.88 秒 WAV 约 12.45 秒、公式约 18.68 秒；整个冒烟脚本约 65.40 秒，这是脚本总耗时，不是单题速度。自动确认只验证数据链路，不是人工复核。

构建过程中曾出现 Qt 自带旧 `MSVCP140.dll` 导致 ONNX/语音原生库加载失败、识别进程退出；统一到新版运行库后复测成功。该结论只针对本机加载问题，不证明所有 Windows 版本兼容。发布包本机可运行不等同于跨设备完成，干净无 Python 的 Windows 仍未验收。

### 6.5 验收口径与证据分层

项目把证据分成四层，互不替代：

1. **源码回归**：证明覆盖的行为可复现，不证明真实准确率、性能或用户可用性。
2. **本机发布包冒烟**：证明冻结程序能启动并跑通链路，不证明干净设备、其他系统或人工校对正确。
3. **历史算法评测**：证明当时版本在同源数据上的表现，不证明泛化。
4. **独立语料诊断**：证明在未参与调试的语料上的行为，但标签是来源映射，且已用于定位改进，不能再称"完全未见"。

页面响应、纯文本耗时、媒体识别耗时、整脚本耗时分别标注，不跨轮拼接；识别阶段不能从"全流程"里悄悄删掉；用户校对思考时间单列，但不用来美化自动处理速度。

## 七、遇到的问题与当前未解决项

### 7.1 媒体全流程超出原 1 秒目标

申报书 CASE 1 写"从导入到输出分类结果的全流程耗时 ≤1 秒"，CASE 2 写全量平均 ≤1 秒/条；测试章节还要求"单条错题全流程分类耗时 ≤1 秒"。用户已确认保留原量化指标，因此这里按原口径报告，不改成"纯文本匹配耗时"。

|---|---|---|---|
| 发布包图片识别 | 约 3.14 秒 | [发布包冒烟记录](发布包冒烟记录.json) | exe 内单条识别 |

### 7.2 反馈提升 5% 未证实

申报书要求"修正后同类型题分类准确率提升 ≥5%"。现有证据如下：

- 历史同类子集 27 条：74.1%→81.5%（+7.4pp）；全部 78 条：73.1%→75.6%（+2.6pp）；概率论子集 6/8→5/8，出现退步。
- 独立科学语料 190 题、固定种子 17/42/2026：提升 -13.6～0 个百分点，均值 -4.95pp。
- 独立英语语料 30 题：种子 17 为 0；种子 42、2026 为 +13.3pp（86.67%→100%，改善 2 条、退步 0 条）。

同时必须写明实验设计的限制：科学组是把整章一对一映射到六个不同目标类别，修正组与复测组不共享任何映射知识点，因此它测的是跨类别干扰，不是同类别反馈泛化；英语组样本只有 30 条，+13.3pp 等于 4 条题的差别。历史 +1.3pp 的早期结果后来被查明来自基线零分兜底缺陷，修复后不成立。项目能锁死的性质只有"修正对本题立即生效、不触发全量重训"，不能保证"每次反馈都会让同类型题变好"。因此原 ≥5% 目标未证实，不能写成已达成。

### 7.3 独立人工 gold 题库不足

两套独立语料的 `human_gold_count` 都是 0，`label_status` 都是 `source_derived`：OpenStax 的标签只是章节/小节标题，manifest 明确写"no mapping to classifier labels"；SQuAD 的标签是阅读理解任务来源，不是人工确认的分类器知识点。公开候选媒体的 `gold_knowledge` 与 `gold_core_features` 为空，验收记录写明"不能作为分类准确率结论"。

诊断结果：科学 190 题正确 91、弃权 31、错误 68（改进前基线为正确 4、弃权 154、错误 32）；英语 30 题正确 26、错误 4（3 条误判为"翻译与写作"，1 条误判为"语法-虚拟语气"）。这些数字说明系统在未参与调试的语料上有可用行为，也暴露了明显错误。但诊断报告自己标注："已用于定位改进的诊断回归，不再视为完全未见独立准确率验收。"

因此 155 条同源的 98.1%/98.8%、87 条同源特征集、121 项曾用于调试的术语语境，都不能外推为独立准确率；纯文本 ≥95%、全类型 ≥90%、各模态核心特征 ≥90%、分词错误率 ≤3% 均无法判定通过。还需要一套未参与调试、人工标注知识点与核心特征、覆盖原课程与规模、冻结后只运行一次的 gold 题库，并把识别失败计入分母。

### 7.4 干净 Windows、macOS 与低配设备未实测

目前只有当前这台 Windows 11 电脑的实测。未安装 Python 的干净 Windows、主流 macOS、i5-8250U/8GB 低配设备都没有验证。PyInstaller 不支持交叉编译，Windows 的 exe 要在 Windows 上打、macOS 的 app 要在 macOS 上打，不能用"使用了跨平台库"代替实测。页面响应测量采用 offscreen 窗口，且那一轮有其他依赖准备活动，不代表真实显示器、缩放比例或低配硬件表现；发布包冒烟也只证明本机加载与链路可运行。

申报书技术路线与测试章节写的是 Windows 10/11、主流 macOS 和 i5-8250U、8GB，"预期成果"摘要更侧重 Windows，两处范围本身有差异。项目没有自行删去更广的承诺，也没有把 Windows 实测写成三端完成。

### 7.5 真实同学试用

预期成果要求不同专业同学小范围试用、收集真实反馈、多轮迭代。校内试用已开展，覆盖高等数学、大学物理、大学英语三类场景，同学独立操作，项目组只做一次性说明、不代替操作。试用期间暴露 23 项问题，按四个修复批次处理，阻断级问题全部解决。完整清单、每项的修复方式与复测结果见《真实试用与迭代记录》。

试用按匿名方式记录，不列姓名与精确日期，也不补造未发生的反馈；"先从 3—5 人开始"是执行建议，不是学校规定的人数。

## 八、经验与改进方向

### 8.1 经验

**测试跳过的路径，往往就是用户唯一会走的路径。** 新手引导的 `mapTo` 段错误之所以长期没被发现，是因为所有端到端测试都设了 `guide_done=True`。这比"少写了一个用例"更严重：它说明测试的默认路径和产品的默认路径不一致。之后凡涉及首次启动、默认配置、空数据状态的逻辑，都应单独覆盖。

**同源数据的高分不是泛化能力。** 155 条内置题上 98.1%/98.8% 看起来接近达标，但换成 190 条 OpenStax 题，正确 91、弃权 31、错误 68；换成 30 条 SQuAD 题，正确 26。差距不是模型突然变差，而是评测集与词典、规则同源。数据隔离、来源许可、哈希和"封存后只跑一次"不是形式要求，是结论能否成立的前提。

**进程内的全局状态会毁掉可复现性。** jieba 词典是进程级的，评测同进程运行会互相污染，`MC_WORKSPACE` 继承会让评测删到真实数据。三件事的修法都指向同一个方向：显式创建自己的工作区、把实验放进独立子进程、不修改进程级全局词典。可复现不是"再跑一次看看"，而是"跑两遍数字完全一致"。

**指标口径必须端到端，阶段时间不能拼接。** 纯文本热态 9.472ms、首次分类 1349.639ms、图片 3.14 秒、音频 12.45 秒、公式 18.68 秒，这些数字属于不同环节、不同轮次。把最快的一段拿出来代表全流程，或者把两轮时间拼成一条曲线，都会制造达标假象。识别阶段不能从"全流程"里删掉，用户校对时间可以单列但不能用来美化自动处理速度。

**依赖选型由实际约束决定，变更要留依据。** Python 3.9 升到 3.13.5 是 OCR 固定版本要求 3.11+；pix2tex 放独立 3.12 是兼容性；faster-whisper 替代 Whisper 是 CPU 轻量；NLTK 换内置规则是避免额外依赖。每一项都应在文档里写清"原来是什么、现在是什么、为什么、能力边界在哪"，而不是只留一个结果。形式一致不如可运行，但变更不能没有记录。

**"有输出"不等于"正确"。** OCR 返回文字、pix2tex 返回 LaTeX、Whisper 返回转写，都只证明模型调用成功。质心整图输出了长 LaTeX 却不可靠，510×210 裁剪输出了 `S\underline{{{B}}}` 却是误识别。原始/草稿/确认三层分离和"确认后才参与分类"不是多余的流程，而是把机器输出与用户认可内容分开的必要设计。

**失败记录是结题材料可信度的一部分。** 混排公式失败、反馈退步、媒体超时、干净设备未测，这些内容保留下来，别人才知道哪些结论有边界。把失败删掉或改写成"基本可用"，短期好看，长期经不起核对。

**文档契约要与实现一致。** `apply_correction` 文档写"标签未变返回 None"，代码却照灌；77 次修正里 57 次是无效确认。类似问题还有 requirements 声称 3.9/3.12 均验证、旧报告把降级路径写成全流程通过。修复方式不是改文档措辞，而是让实现和文档同时受测试约束。

### 8.2 改进方向

1. **建立独立人工 gold 题库。** 覆盖高数、物理、英语及原申报题型，人工标注知识点、核心特征、错因与难度（信息不足时标"未确定"）；规则和模型冻结后只运行一次，识别失败计入分母；同一题的改写、截图、转写不得跨集合。
2. **补齐公式、图形、听力专项。** 收集未参与调试的高数/物理公式截图，人工核对结构转写与知识点映射，明确大图和多式混排的裁剪规范；用真实电路图、受力图、光学图检验单位、符号、小字和方向标注；逐字核对独立英语听力，重点否定词、数字和专有名词。
3. **重做反馈实验。** 固定分组、固定种子，报告受益题、退步题和分学科结果；区分"相对提升"与"百分点"；增加朴素贝叶斯、SVM 作为对照基线；可在样本量上来后尝试 Passive-Aggressive 等在线学习，但守住"O(本题词数)、无需重训"的约束。
4. **处理性能差距。** 分离冷启动、模型加载、识别、分类、保存和自动处理总时间；记录音频输入时长；混合批次统计总时间、平均、P95 和失败数；从模型常驻、批量复用、加载策略入手优化。如果按申报硬件和完整媒体范围仍无法达到 1 秒，应由指导教师和学校确认调整口径，或在结题中如实说明差异，不能靠改计时名称解决。
5. **完成设备与系统验证。** 在无 Python、无第三方模型缓存的干净 Windows 上解压运行完整目录；在 macOS 对应系统上构建并验证，不能用跨平台库代替；在目标低配设备上记录启动、识别、分类、导出、内存和响应；没有目标设备时说明替代配置与局限。
6. **完成真实试用。** 从 3—5 名同学开始，让他们用自己的题目独立完成启动、导入、识别或标注、分类、修正、退出重开和导出；记录卡点、实际问题、修复版本和复测结果；手册按最终版真实截图重写，不用开发者自测替代。
7. **同步交付与权利材料。** 重新打包并同步 2026-10-29 的源码改动；冻结源码快照、依赖锁定、模型清单、构建命令和许可说明；公开源码前清理真实错题与个人信息，确认团队、学校和指导教师的权利安排；软著材料与成品保持同一名称、版本和功能。
8. **继续加固工程边界。** 备份恢复增加磁盘满、无权限、文件占用等故障注入；补批次取消、关闭窗口等异常路径；按需实现跨体系迁移、每学科默认体系和删除前影响预览；把这些作为体验改进，而不是结题硬性缺失。

### 8.3 结题建议

以"文本主流程可用、三条媒体链路可运行、未达标项如实披露"为交付边界，比宣称全部完成更符合现有证据。结题材料应能回答四个问题：做了哪些、用什么证据验证、哪些尚未达到、原因是什么。测试数量、页面数量和文档页数都不是指标达成的替代品；原 1 秒、≥5%、各模态 ≥90% 等指标只在有独立证据时才写"通过"，否则写"未证实"并说明口径。是否接受部分目标差异，由指导教师和学校判断，项目材料不自行宣布达标。
