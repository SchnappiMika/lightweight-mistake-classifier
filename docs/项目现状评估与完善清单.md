# 错题分类软件现状评估与完善清单

> 这是修复前的评估记录，以下“状态”和 190 项测试结果保留为当时的基线。当前状态统一见 [开发进度与验收](开发进度与验收.md)；[第一批修复与后续计划](第一批修复与后续计划.md)保留首批记录。请勿把本页的历史问题当作仍未修复的清单。

本清单用于把现有软件完善到可以实际使用、可以据实演示校创成果，并进一步准备软件著作权登记材料的状态。评估依据是项目申报书、当前源码、现有文档及本次隔离环境验证，不依据申报书的日期判断项目可行性。

用户已确认：学校没有另行提出的结题成果要求；申请软著是个人希望增加的成果；目前连软件的启动方式也不够明确。因此，本清单以申报书中的功能与预期成果作为对照，学校最终验收结果仍由学校认定。

## 一 当前判断

这个项目具备继续完善并准备申请软著的现实基础。传统算法、Python 桌面程序、使用开源依赖，都不意味着不能申请软著。关键是实际形成的软件作品、相应权利归属，以及与软件一致的登记材料。软著登记也不等同于对分类准确率、算法创新程度或软件质量的认证。

现有项目已经有界面、数据模型、分类引擎、导入导出、人工反馈和测试，继续开发的基础比较充分。但当前更适合定位为“已有主要模块的功能原型”。在可靠启动、编辑正确性、自建体系真正生效、多模态识别交付、数据恢复、真实评测等方面，仍有具体缺口。当前不宜在结题材料或软著说明书中直接宣称申报书的所有目标均已完成。

本轮工作是评估与清单整理，未修改原申报书或软件业务逻辑，未清空用户实际工作区。本次依赖安装、测试及流程探针使用独立环境和临时数据。

## 二 本次实际验证了什么

验证环境为当前 Windows 主机、Python 3.13.5、独立虚拟环境；按当前 requirements.txt 安装核心依赖，另安装 pytest。Qt 操作流程验证采用 offscreen 模式，不代表已完成真实屏幕、输入法、缩放比例和音频设备验收。

| 项目 | 本次结果 | 能说明什么 |
|---|---|---|
| 现有自动化测试 | 190 项通过，8 条警告，约 26.20 秒 | 既有用例通过；不覆盖下面全部实际操作缺陷 |
| 现有 155 条数据的知识点分类 | 98.1%，纯文本 98.8% | 内置数据上的回归表现较好 |
| 主评测运行耗时 | 均值约 8.3ms，P95 约 13.3ms | 本次数据的算法流程较快；不能代表真实图片、音频处理耗时 |
| 多特征消融对照 | 单通道 98.1%，多特征 98.1% | 总准确率没有提高；不同学科存在得失 |
| 反馈实验 | 同类子集 74.1%→81.5%，全复测集 73.1%→75.6% | 有正向实验结果，但同类子集仅 27 条，证据不够稳健 |
| 反馈实验的概率论子集 | 6/8→5/8 | 部分题会因学习而受损，不能保证反馈永不降低其他题的准确率 |
| 特征评测 | 文本 100%，公式 100%，图形 100%，英语 93.3% | 现有标注集上的结果；不等同于真实识别准确率 |
| 真实媒体数据覆盖 | 155 条评测记录均未关联媒体路径；图形 8 条、听力 3 条 | 本次分类评测没有验证从真实图片、音频中识别信息的完整流程 |
| 识别引擎状态 | pix2tex、PaddleOCR、Whisper、NLTK/WordNet 均不可用，走降级路径 | 按核心 requirements 安装后，尚不具备开箱即用的全部识别能力 |

本次没有验证：实际 exe 打包产物、干净 Windows 电脑双击运行、真实 OCR/公式识别/音频转写、MacOS、指定低配机器、长时间连续使用、真实用户独立操作。不能把这些项目标成“已通过”。

## 四 P0 清单 演示和交付前优先修复

P0 表示会造成操作错误、结果不可信、数据风险，或阻止普通用户使用。下面各项均需有明确验收记录。

### 01 提供明确且可靠的启动方式

- 状态：缺少交付产物。当前目录没有 dist 中的可执行文件，也没有双击启动脚本。检查时默认 Python 中缺少全部核心依赖；本次另建的验证环境不等同于用户日常启动环境。
- 改进：确定一个主启动入口，优先提供 Windows 可执行包；开发运行另提供检查 Python、依赖、工作目录及日志的启动脚本。缺依赖时显示可理解的处理办法。
- 验收：一台没有开发环境的 Windows 电脑解压后可以双击启动；中文路径下正常运行；用户知道打开哪个文件、数据保存在哪里。

### 02 修复关键词编辑框输入倒序

- 状态：已复现。向分类体系的关键词编辑框依次输入 abc，实际内容变为 cba。
- 原因：编辑触发提交，提交广播体系变化，体系树刷新并重新选中标签，重新载入编辑器导致光标位置被重置。位置：app/ui/pages/page_scheme.py 的 refresh_tree、_load_label、_on_kw_changed、_commit。
- 改进：避免每次输入都完整重建树与编辑器；可采用延迟保存、局部刷新，并保留光标、选区和输入法组合状态。
- 验收：连续输入、删除、换行、粘贴、中文输入法选词均按正常顺序保存，光标不跳动。

### 03 让选中的自建体系真正用于分类

- 状态：已复现。新建高数体系并选中后，对高数题分类，实际使用的仍是“高等数学（默认体系）”。
- 原因：page_classify.py 的 _start 按学科调用 scheme_for_subject；Repository.scheme_by_subject 返回该学科第一套体系，没有优先使用用户选择。
- 改进：明确提供“使用当前体系”和“按学科自动分配体系”两种规则，并允许为每门学科设置默认体系。
- 验收：自建高数体系中只有自建标签时，分类结果来自该体系；切回内置体系后按内置规则分类。

### 04 修改题目后作废旧分类和旧特征

- 状态：已复现。把已判为“定积分及其应用”的题干改为“求解一阶线性微分方程的通解”，记录仍然 classified=True、保留旧特征和旧标签，“未分类”数量为 0。
- 影响：用户再次点击“一键分类（未分类）”不会处理修改后的题；反馈学习也可能读取旧特征。
- 改进：题干、标注、学科、题型、附件变化后，明确标记“内容已修改，待重新分类”，作废相关缓存和不再适用的人工确认状态。
- 验收：修改上述任一字段后，旧结果不能被当作新内容的有效结果；下一次分类和反馈使用新内容。

### 05 防止跨体系分类保留无效标签

- 状态：已复现。在一套体系中人工确认后，向另一套体系应用分类结果，scheme_id 已改变，但旧人工确认标签仍被保留，该标签不存在于新体系中。
- 原因：app/core/classify/engine.py 的 apply_result 对所有 corrected 维度直接跳过，没有核对修正属于哪套体系。
- 改进：人工确认记录与体系和版本绑定；切换体系时明确迁移或作废，不保留悬空标签。
- 验收：每条结果的标签均能在对应体系中找到；切换体系、删除体系、恢复内置体系后保持一致。

### 06 标签更名和删除后同步历史题目

- 状态：更名未同步已复现。把标签改名后，题目中的 label_names 仍保留旧名称，导出也会使用旧名称。删除标签后的引用清理从代码检查也未见实现，需补专项用例。
- 改进：基于稳定 ID 统一解析名称；更名同步展示及导出；删除有引用的标签时提示迁移到其他标签或标记待复核。
- 验收：历史题目、结果页、统计、Excel 中名称一致；不会出现已删除标签仍作为有效结果的情况。

### 07 不把空题和识别失败题算成成功分类

- 状态：已复现。空题未提取到有效特征、没有标签，应用结果后仍标为 classified=True。
- 改进：至少区分“待处理、处理中、已分类、待复核、识别失败、分类失败”；无有效特征时保持待补充状态，说明原因。
- 验收：空题、坏图、无声或损坏音频、没有识别引擎且无标注的媒体题，都不会混入成功数。

### 08 清空学习成果必须覆盖全部体系

- 状态：已复现。某体系的历史学习增量已落盘，在新 AppContext 中尚未创建对应引擎时执行清空学习成果，该体系的增量仍然保留。
- 原因：app/ui/context.py 的 reset_optimization 仅遍历当前进程缓存的引擎。
- 改进：从持久化层统一清空全部体系的学习数据，并同步缓存、权重、反馈日志与题目状态。
- 验收：学习后重启，不进入该学科页面，直接清空学习成果，再重启进入该学科，历史学习计数和增量均为空。

### 09 隔离评测脚本和真实数据

- 状态：代码确认存在风险。tools/evaluate.py 使用继承的 MC_WORKSPACE，并在 _run_one 中直接 shutil.rmtree(ws)。如果用户把该变量指向真实数据目录后运行评测，会清空该目录。本次评测已显式使用独立临时路径。
- 改进：评测始终使用自己创建的临时目录；删除前校验目录归属；禁止把业务工作区作为评测清理目标。
- 验收：即使外部设置 MC_WORKSPACE 指向有数据的真实工作区，评测也完全不修改它。

### 10 增加可验证的备份和恢复

- 状态：现有原子写入只能减少单文件写到一半的问题，不能保证所有数据永不丢失。目前没有用户可用的完整备份恢复入口；异常弹窗直接宣称“数据已经自动保存”，没有相应保存结果证明。
- 改进：加入工作区备份包、恢复前备份、损坏数据提示、恢复检查；迁移时重定位附件。检查题目、体系、学习数据之间的一致性。媒体路径目前按字符串保存，不能仅靠复制工作区就保证换电脑可用。
- 验收：从备份恢复到另一个用户目录或另一台电脑，题目、附件、体系、反馈可用；保存失败会明确提示，不声称已经保存成功。

## 五 P1 清单 补齐承诺的功能和主要使用流程

### 11 真正交付三条媒体识别流程

- 状态：有适配代码，未验证实际能力。默认依赖未安装识别引擎；tools/build.py 还明确排除了 torch、pix2tex、PaddleOCR、Whisper 等依赖。
- 改进：在基础文本版之外，提供与申报目标对应的本地识别安装包或模型组件包，逐条打通公式图片→LaTeX、图形图片→文字、音频→转写→分类。
- 验收：不用人工事先填写知识点名称，真实图片和音频可以得到识别结果，再完成分类和归档。公式截图和包含文字、图形的整题截图分别验收。

### 12 提供模型准备和真正的离线模式

- 状态：代码使用 WhisperModel('base')、whisper.load_model('base')、LatexOCR() 和 PaddleOCR 默认初始化。即使业务代码没有 requests，第三方库首次加载也可能下载模型；目前没有本地模型路径配置和离线完整性验证。
- 改进：固定引擎、模型和依赖版本，准备本地模型目录、校验值、组件安装说明与许可证；运行阶段采用仅本地加载，缺文件时给出提示和模型导入入口。
- 验收：清空第三方用户缓存后，在断网电脑仅用交付的组件和模型文件，三条识别流程仍可成功。

### 13 让环境自检反映真实可用状态

- 状态：主窗口的 _on_warm 和环境弹窗会调用 engine_report；各引擎 status 又会触发模型初始化。装了重依赖后可能在界面线程加载模型或等待下载，这个路径本次尚未实测。
- 改进：把“组件已安装、模型已准备、模型正在加载、可识别、识别失败”分开；探测与加载放后台；失败后允许重新检测，无需重启。
- 验收：打开环境自检不会冻结窗口；用户能知道缺什么、如何处理；界面提示与实际识别状态一致。

### 14 识别结果可查看 可编辑 可重试

- 状态：目前能在分类结果说明里看到截断的 LaTeX、OCR 或转写摘要，缺少完整的识别结果校对流程。
- 改进：保留原图或音频、完整识别文字、识别状态；允许先修改识别结果再分类；图像支持放大查看，公式提供可读预览。
- 验收：OCR 把一个关键字认错后，用户可在界面改正、重新分类，并保存修改后的结果。

### 15 修复表格附件路径并统一复制附件

- 状态：已复现。CSV 中写“image.png”，图片与 CSV 同目录，导入后仍保存裸相对路径，应用从项目目录检查时找不到附件。表格导入也未像直接媒体导入一样统一复制附件进工作区。
- 改进：以源表格所在目录解析相对路径；校验存在性；复制到受管理的媒体目录；返回具体行号和失败原因。
- 验收：把同一批表格和图片移动到不同目录再导入，仍能找到附件；移走原始文件后，软件内已导入记录仍可预览。

### 16 统一实际支持的文件格式与导入预览

- 状态：界面允许选择 xls，但 requirements 没有明确提供对应读取依赖；CSV 直接用 pandas 默认编码，未复用 TXT 的编码兜底。具体旧格式与编码组合需实测。
- 改进：确定并公布支持范围，补齐对应依赖或收紧文件选择；增加列映射、多工作表选择、编码选择及导入预览。
- 验收：对声明支持的每种格式提供成功和错误用例；表头识别失败时由用户选择题干列，不静默拿错误列当题干。

### 17 重复导入和部分失败可处理

- 状态：同一文本两次导入会生成两条记录，已验证。ImportWorker 的多个文件批量导入遇到异常时会返回空列表，已解析的前序文件缺少保留结果与重试流程。
- 改进：增加可选去重和重复提示；逐文件或逐行收集成功与失败结果；保留成功项，导出失败清单。
- 验收：批量选择正常文件与坏文件，正常项可导入；再次导入同一批数据不会在用户不知情时重复堆积。

### 18 补齐后台任务的状态和互斥

- 状态：存在后台线程，但导入缺少明显的重复启动保护；分类期间其他页面仍可修改共享题目或体系。引擎建库失败时只弹提示，未见统一恢复进度与继续队列的处理。停止后仍按原批次总数报告完成，需修正。
- 改进：统一任务状态；批处理期间锁定或隔离相关编辑；支持取消、失败后继续；按成功、失败、跳过、取消分别计数；导出和大批导入也避免阻塞界面。
- 验收：连续点导入、分类时切页编辑、分类中停止、建库报错、处理中关窗，均能结束任务、显示准确状态，并继续下一次操作。

### 19 让导出与实际分类体系对应

- 状态：导出页以学科筛选，使用一套当前体系决定导出列；混合不同体系或不同自定义维度的数据时可能缺列或混淆。本次尚未完成全部混合体系组合验证。
- 改进：支持按分类体系筛选，跨体系导出时合并实际维度并保留体系来源；记录未分类、待复核、识别失败状态；完整备份与复习导出分开提供。
- 验收：两套同学科但维度不同的体系，导出结果不会遗漏其中一套的自定义分类信息。

### 20 补齐可读的复习导出

- 状态：当前 Excel 为表格导出。检查导出文件时，题干单元格没有自动换行，未设置打印区域或按页宽缩放；源码也没有图片嵌入或 LaTeX 排版实现。不能据此承诺“直接打印就是完整错题本”。

## 八 推荐执行顺序与每阶段交付物

| 阶段 | 重点 | 交付物 | 完成标准 |
|---|---|---|---|
| 第一阶段 | P0 的启动、编辑、体系路由、缓存和数据一致性 | 可启动的文本分类版本、已确认缺陷的修复及回归记录、备份机制 | 用户能独立完成一条真实文本题的完整流程，修改后结果正确更新 |
| 第二阶段 | 三条媒体识别链路与离线模型准备 | 可实际安装的识别组件、真实图片/音频用例、识别校对界面 | 断网环境从原始媒体到分类归档成功 |
| 第三阶段 | 导入导出、任务控制、搜索和复习材料 | 完整导入预览、失败重试、可读导出、备份恢复验证 | 批量真实数据可连续使用，不能只演示内置示例 |
| 第四阶段 | 独立评测、设备验证、实际试用 | 测试数据、问题记录、客观报告、稳定发布包 | 申报目标逐项有结果，未达成项如实交代 |
| 第五阶段 | 结题资料与软著材料 | 最终源码、操作手册、演示资料、权利资料和登记材料 | 材料与最终软件一致，权利人明确 |

这些阶段是开发顺序，不是对完成日期、学校结题结果或软著受理结果的承诺。首先解决第一阶段，收益最大；不要先增加大量页面或生成漂亮材料来替代功能修复。
